# Wildbox Security Status

What is known about Wildbox's security today, including what is still wrong.
This page replaces an earlier report that marked every audit finding "Fixed"
and every check "PASS"; several of those claims did not hold when they were
checked against the code.

**Current release**: v0.11.2. Its changes, and those of every earlier
release, are listed in [CHANGELOG.md](https://github.com/fabriziosalmi/wildbox/blob/main/CHANGELOG.md).  
**Checked against**: `main` on 4 October 2026. Each check below names how it
was made, so it can be repeated.

To report a vulnerability, follow
[SECURITY.md](https://github.com/fabriziosalmi/wildbox/blob/main/SECURITY.md);
do not open a public issue.

| Gateway requires authentication on service APIs | PASS | Every `/api/v1/<service>/` location in `wildbox_gateway.conf` calls `auth_handler.authenticate()`; identity validates tokens itself |
| Every gateway route requires the API-key scope it documents | PASS | `ROUTE_SCOPES` in `auth_handler.lua` holds one row for each authenticated route, matched by the path nginx chose the location for; a path with no row requires `admin`. `open-security-gateway/test/route_scope_tests.sh` runs the production image and configuration, reads every location that calls `authenticate()` and fails for one without a pin, and checks each pin per method: a key with no scope is refused and told the pinned scope, and a key holding exactly that scope reaches the upstream path. `GET /api/v1/tools` needs `tools:read`, and a location that rewrites its path is mapped by the path it was chosen for ([#647](https://github.com/fabriziosalmi/wildbox/issues/647)) |
| API-key scopes are checked by the gateway and again by data, guardian and tools | PASS | The gateway forwards what it decided on: `X-Wildbox-Auth-Type` (`session` or `api_key`) and, for an API key, `X-Wildbox-Scopes`. `authenticate()` sets both and removes a client's own, and a location that does not authenticate forwards neither (`auth_handler.lua`, `proxy_params.conf`). The data service requires `data:ingest` on its ingest route and `read` or `write` on every other one, so a sensor's key does nothing else there; guardian requires `data:read`, `data:write` or `data:delete` by method in its middleware; tools requires `tools:execute` to run a tool or cancel a task (`open_security_shared.scopes`, `gateway_auth.require_scope`). All three refuse a request that does not state its credential, and a header they cannot read. The gateway's check stands alone for reading tools and tasks and for the agents, responder and CSPM services; and a call one service makes for a user states `service`, which is not limited by the scopes of the key that started the work ([#637](https://github.com/fabriziosalmi/wildbox/issues/637)). Tested in `tests/shared/test_scopes.py` and `test_gateway_scopes.py`, in `tests/unit/test_api_key_scopes.py` of data, guardian and tools, in `open-security-gateway/test/scope_forwarding_tests.sh` (the forwarded value is the key's scopes; a client's headers are dropped) and `scope_vector_tests.sh` (the gateway and the services decide alike, on 200 pairs), in `route_scope_tests.sh` (every route of the production configuration tells the service the key's scopes), and through the gateway in `tests/integration/test_api_key_scopes_backends.py` |
| Gateway secret sent only for authenticated callers | PASS | `proxy_params.conf` sends `X-Gateway-Secret` from `$wildbox_gateway_secret`, which the server block seeds empty and only `authenticate()` fills in (`auth_handler.lua`). The identity passthrough and the dashboard forward no secret and drop a client's own ([#664](https://github.com/fabriziosalmi/wildbox/issues/664)). Tested in `open-security-gateway/test/ci_auth_tests.sh` and `tests/integration/test_identity_access_scope.py` |
| Gateway secret and caller credentials sent only to the services that validate them | PASS | n8n, behind `/api/v1/automations/`, is not a Wildbox service and used to be sent `X-Gateway-Secret`, the caller's user, team and role and, from a browser, the session JWT in the `auth_token` cookie. The gateway no longer routes to n8n at all (next row). The `auth_token` cookie is removed on every authenticated route, and a client's `X-API-Key` no longer reaches the dashboard or identity's own routes ([#711](https://github.com/fabriziosalmi/wildbox/issues/711)). `open-security-gateway/test/upstream_header_tests.sh` runs the production image and configuration, classifies every location that proxies (it fails for one it does not know) and checks what each upstream receives of a request carrying a session token, an API key, the session cookie and forged gateway headers. `tests/scripts/test_gateway_authenticated_locations.py` fails for a location whose upstream is not a Wildbox service or the dashboard |
| n8n is not reachable through the gateway | PASS | `/api/v1/automations/` proxied to n8n's editor, REST API and webhooks for every registered session of every team, and on an instance with no owner account yet the first caller could create it. The location, its scope-map row and the `third_party` upstream kind are removed: the path answers 404 with or without a credential, which `upstream_header_tests.sh` and `route_scope_tests.sh` check against the production image for a session, a `tools:admin` key, an `admin` key and an unlimited key. n8n's editor is published on `127.0.0.1:5678` only (`tests/scripts/test_automations_exposure.py`, `scripts/check_container_hygiene.py`), and the `N8N_BASIC_AUTH_*` variables, which n8n 1.x ignores, are no longer set, generated or required. The operator creates n8n's owner account right after the first start; until then whoever reaches port 5678 can ([#714](https://github.com/fabriziosalmi/wildbox/issues/714)) |
| Identity admin metrics restricted to superusers | PASS | `GET /api/v1/admin/metrics` authenticates the bearer token and requires `is_superuser`; the gateway secret alone no longer opens it ([#664](https://github.com/fabriziosalmi/wildbox/issues/664)). Tested anonymously, with a forged and with the real secret, as a team owner and as a superuser in `open-security-identity/tests/unit/test_admin_metrics_access.py` and `tests/integration/test_identity_access_scope.py` |
| tools answers only four routes without the gateway's identity | PASS | `/health`, `/metrics`, `/openapi.json` and `/api`, none of them routed by the gateway. `/health` and `/api` report the status, the service's version and two counts, and no longer name the environment, the settings or the loaded tools to whoever reaches the service port ([#721](https://github.com/fabriziosalmi/wildbox/issues/721)). The four `/api/system/` routes, which also reported the debug flag and the health of the other services, were removed ([#646](https://github.com/fabriziosalmi/wildbox/issues/646)). `open-security-tools/tests/unit/test_system_surface.py` calls every operation in the service's schema without credentials and expects 401 |
| Each team reaches only its own data | PASS for guardian, data, responder and cspm | guardian scopes its models, routes and Celery tasks to the caller's team ([#642](https://github.com/fabriziosalmi/wildbox/issues/642)); data stores and serves sensor telemetry per team ([#641](https://github.com/fabriziosalmi/wildbox/issues/641)). The integration suite registers two accounts and checks each service through the gateway: `test_guardian_tenancy.py`, `test_data_tenancy.py`, `test_data_cross_tenant.py`, `test_telemetry_tenancy.py`, `test_responder_tenancy.py` and `test_cspm_tenancy.py` all passed on `main` (Integration Tests, commit `bcbc569f`) |
| Guardian e-mails a team's data to that team's people only | PASS | Every e-mail goes through `notify_team` (`apps/core/notifications.py`): to the addresses the team typed into the alert rule or report schedule concerned, to the vulnerability's assignee, or to the team's owners and admins, and never to a platform-wide address ([#678](https://github.com/fabriziosalmi/wildbox/issues/678), [#705](https://github.com/fabriziosalmi/wildbox/issues/705)). guardian keeps no address: its worker asks identity when it sends (`POST /internal/team-contacts`), which answers active members of the team asked about only, so a former member, a deactivated account and an old address receive nothing, and guardian checks the answer again before using it. The worker presents `GUARDIAN_CONTACTS_SECRET`, not `GATEWAY_INTERNAL_SECRET`, which it does not hold; identity does not start when the two are equal. Without a mail server nothing is printed to the log and each notification is recorded as not sent. No address is written to a log. Tested in `open-security-guardian/tests/unit/test_notification_delivery.py` (every notification, for two teams: each reaches its own people and names nothing of the other), `open-security-identity/tests/unit/test_team_contacts.py`, `tests/scripts/test_guardian_mail_wiring.py` and, through the gateway, `tests/integration/test_guardian_notifications.py`. The addresses a team types into a rule or a schedule are used as they are: removing a person from the team does not remove their address from a rule |
| Guardian's answers name no internal host | PASS | The `next` and `previous` links of a paginated list are relative references under the gateway's `/api/v1/guardian/` path, with no scheme and no host; they were absolute URLs on `open-security-guardian`, the Host the gateway presents guardian ([#643](https://github.com/fabriziosalmi/wildbox/issues/643)). The path comes from `X-Forwarded-Prefix`, a literal in the gateway's guardian location that replaces a client's own; guardian reads no host header for a link. `tests/integration/test_guardian_pagination_links.py` follows the links through the gateway, with and without forged `X-Forwarded-*`, `Forwarded`, `SCRIPT_NAME` and `Host` headers; `open-security-guardian/tests/unit/test_gateway_links.py` checks the header against the gateway configuration |
| Guardian's rate limit is the configured one | PASS | `docker-compose.yml` passes `GUARDIAN_RATE_LIMIT_USER` to guardian, which refuses to start on a malformed value and counts requests per gateway user, not per address ([#645](https://github.com/fabriziosalmi/wildbox/issues/645)). Its throttle for anonymous callers is removed: no anonymous request reaches `/api/`, and it refused the container's own health probe. Tested in `open-security-guardian/tests/unit/test_rate_limit.py` |
| Guardian stores no credential of a scanner or an external system | PASS | A scanner's `api_key` and `password`, an external system's `auth_config`, a webhook endpoint's `secret_token` and a notification channel's `config` were kept in guardian's database as plain text (the help text of one said "Encrypted"), were never returned by the API and had no reader: guardian connects to no scanner, contacts no external system, receives no webhook and delivers nothing through a channel. The five columns are dropped, with their values blanked first because PostgreSQL's `DROP COLUMN` leaves a column's bytes in the row, and the API answers `400` for a value sent in one of them instead of accepting a secret it would discard ([#728](https://github.com/fabriziosalmi/wildbox/issues/728)). No encryption key was added, since nothing is left to encrypt. `open-security-guardian/tests/unit/test_no_stored_credentials.py` sends each secret through every write route and reads every table afterwards, runs the migrations on rows that hold secrets, and fails for a model field or a served serializer field named like a secret. Backups written before the upgrade still hold what was stored: see the [deployment guide](../guides/deployment.md#what-a-backup-contains) |
| Scans reach no internal target unless the operator lists it | PASS for guardian's scans and the tools service's network tools | Both decide with one implementation, `open_security_shared.target_policy`: private, loopback, link-local, multicast, reserved, shared and cloud-metadata addresses are refused, IPv4 and IPv6, an IPv4 address embedded in an IPv6 one included, and a range is refused whole when one address of it is internal. guardian's asset discovery and port scans, which run from a worker inside the stack's networks, had no such check: a discovery of the worker's loopback, of the stack's Docker network or of a cloud metadata address was accepted and run ([#748](https://github.com/fabriziosalmi/wildbox/issues/748)). They are now refused where the target is typed (`400`, nothing queued) and again in the worker, unless the range is in `GUARDIAN_ALLOWED_INTERNAL_TARGETS`, which is empty by default and stops guardian and its worker at start-up when malformed. The tools service's policy ([#614](https://github.com/fabriziosalmi/wildbox/issues/614)) answers as before, with `TOOLS_ALLOWED_INTERNAL_TARGETS`; neither service reads the other's list. What remains is in the tools README: most tools resolve a checked name again when they connect. One vectors file, `tests/shared/target_policy_vectors.json`, is run by the shared package's, the tools service's and guardian's suites; tested also in `open-security-guardian/tests/unit/test_scan_target_policy.py` and, through the gateway, in `tests/integration/test_guardian_scan_targets.py` |
| Self-service API-key routes reach the caller's keys only | PASS | The self-service routes match the caller's user ID as well as the team, so a member cannot read or revoke a teammate's key; a team owner or admin revokes through the team route ([#664](https://github.com/fabriziosalmi/wildbox/issues/664)). Tested in `tests/integration/test_identity_access_scope.py` and `test_api_key_revocation.py` |
| API keys stored as keyed digests | PASS | identity stores an HMAC of each key, keyed with `API_KEY_HASH_SECRET` (`app/auth.py`). `docker-compose.yml` and `docker-compose.prod.yml` refuse to start without it, and identity refuses to start in production without it ([#648](https://github.com/fabriziosalmi/wildbox/issues/648)). Tested in `open-security-identity/tests/unit/test_api_key_hash_secret.py` |
| Agent tasks reachable by their owner only | PASS | Reading or cancelling an analysis fails closed: a missing owner record or another user's task answers 404. The analyze rate limit is keyed by the verified gateway user, with an optional per-team ceiling, instead of the gateway's address ([#650](https://github.com/fabriziosalmi/wildbox/issues/650), [#651](https://github.com/fabriziosalmi/wildbox/issues/651)). The agent's tools call the tools, data and guardian services with the identity of the user who submitted the analysis, so each service answers for that user's team; the agents service holds no key that sees every team ([#652](https://github.com/fabriziosalmi/wildbox/issues/652)). The two tools that read a team's own data (its indicators and Guardian vulnerabilities) are not given to the model unless the operator names them in `AGENT_TEAM_DATA_TOOLS`: enabling one sends what it returns to the model provider and places it in the model's context beside text fetched from the internet, a prompt-injection path the prompt alone does not close. Tested in `test_tools_act_as_the_caller.py`, `test_team_data_tools.py` and `tests/integration/test_agents_tools_identity.py` |
| Every API endpoint enforces authentication | Not verified | Not checked endpoint by endpoint behind the gateway |

| Account lockout after failed logins | PASS | After 5 failed password logins an account, registered or not, is refused with 429 for 15 minutes, whatever the password; a successful login clears the counter ([#509](https://github.com/fabriziosalmi/wildbox/issues/509)). Tested in `tests/integration/test_login_lockout.py` |
| CORS without wildcards, for listed origins only | PASS | No `allow_origins=["*"]` or wildcard `Access-Control-Allow-Origin` in service code or gateway config. The gateway decides CORS for the API in one place (`lua/cors.lua`, `includes/cors.conf`): it answers a preflight, and names an origin in a response, only for the origins in `CORS_ORIGINS`, always the specific origin with `Vary: Origin`, and removes what a service sets. It does not start with an entry that is not an origin, a wildcard included. A preflight used to be answered 405 in the production configuration and the harness checked another one ([#712](https://github.com/fabriziosalmi/wildbox/issues/712)). Tested against the production image and configuration in `open-security-gateway/test/cors_tests.sh`, and at startup in `startup_config_tests.sh` |

## History

The November 2024 platform audit (its report, remediation checklist and
improvements summary) is no longer published: it described code that has since
changed, and its findings are superseded by this page. The tools service
audit of November 2025 is not published either, for the same reason; it is
kept in the repository as
[docs/security/tools-service-audit.md](https://github.com/fabriziosalmi/wildbox/blob/main/docs/security/tools-service-audit.md).

The audit rounds of February 2026 (v0.5.2 to v0.5.5) and every later security
change are recorded release by release in
[CHANGELOG.md](https://github.com/fabriziosalmi/wildbox/blob/main/CHANGELOG.md).
